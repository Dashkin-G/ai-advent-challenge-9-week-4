# CLAUDE.md

Служебный файл для ИИ-ассистента (Claude Code), помогающего проходить курс по
разработке ИИ-агентов. В git не входит (см. «Этот файл — вне git»).

Файл самодостаточен: всё нужное про курс, проект и правила — здесь, заглядывать
в соседние репозитории прошлых недель не требуется.

---

## Что это за проект

Учебный проект курса. Цель курса — по максимуму использовать ИИ-агентов: и для
самой разработки (через Claude Code), и для построения сервиса, который через
внешний API подключается к моделям и наращивает функционал ИИ-системы.

Каждый день приходит новое задание (скриншотом из телеграм-канала курса),
формат сдачи — **видео + код**. Проект развивается инкрементально: одна кодовая
база, без переписывания с нуля.

**Нумерация дней сквозная по курсу.** Первая неделя — дни 1–5
(`../ai-advent-challenge-9-week-1`), вторая — дни 6–10
(`../ai-advent-challenge-9-week-2`), третья — дни 11–15
(`../ai-advent-challenge-9-week-3`). **Четвёртая неделя начинается с дня 16, это
отдельный новый репозиторий, текущий. Тема недели — MCP.**

### Что было в прошлых неделях (код сюда не переносился)

- **Неделя 1 (дни 1–5), веб-чат на FastAPI к LLM:** минимальный чат; контроль
  ответа (`max_tokens`, стоп-строка, `finish_reason`); способы рассуждения со
  стримингом и судьёй-LLM; температура и «сырой обмен»; сравнение версий
  моделей с метриками время/токены/стоимость.
- **Неделя 2 (дни 6–10), агент:** `Agent` с паспортом, инструментами и циклом
  ReAct; SQLite вместо JSON; свой счётчик токенов; суммаризация истории; три
  стратегии управления контекстом (Sliding Window, Sticky Facts, Branching).
  Интерфейс тогда переехал с веба на PySide6.
- **Неделя 3 (дни 11–15), память и состояние:** модель памяти из трёх слоёв
  (краткосрочная / рабочая / долговременная) с маршрутизатором; персонализация
  через профиль пользователя; состояние задачи как конечный автомат; инварианты
  и ограничения; контролируемые переходы с отказами.

### Главный урок третьей недели, который определил четвёртую

В конце недели 3 пользователь сравнил наш экран с работами других участников:
*«у них как будто сделано для людей, а у нас — для нейронок»*. Плотный
отладочный вывод мелким моноширинным шрифтом формально показывал всё задание, но
пользоваться этим было нельзя. Отсюда требования, которые действуют и сейчас:

1. экран строится вокруг задачи человека, а не вокруг пунктов задания;
2. **правило трёх секунд**: с любого экрана видно, что происходит, чего ждут от
   человека и что будет дальше;
3. крупно и с воздухом: базовый текст 15–16 px, заголовки 20+, состояние —
   визуальными элементами, моноширинный шрифт только для кода и сырых данных;
4. техническая изнанка — не в каждый ответ, а в отдельный блок, который можно
   раскрыть (в этом проекте это свёрнутый журнал «Обмен по MCP»);
5. говорить по-человечески: «MCP-сервер выключен в панели CRM», а не
   «MCPError: INTERNAL_ERROR».

## День 16 (выполнено): свой MCP-сервер и агент, который к нему подключается

**Задание дня.** Установить MCP SDK / клиент (или поднять MCP-сервер, если
используется локальный вариант). Написать минимальный код, который устанавливает
MCP-соединение и получает от MCP список доступных инструментов. Проверить, что
соединение устанавливается и список инструментов корректно возвращается.
Результат — код, который подключается к MCP и выводит список инструментов.

**Рамки, заданные пользователем до начала работы:**

- всё локально, без развёртывания во внешнюю сеть;
- **одно приложение FastAPI**, в котором поднимается и MCP-сервер, и чат с
  агентом; условно это два приложения, но запускаются одной командой и на одном
  порту — отдельный порт каждому не заводить;
- в браузере экран делится на два окна: слева чат с агентом (кнопка
  подключения, проверка соединения, список полученных инструментов), справа
  фронтовая часть MCP («условно CRM»), где можно что-то менять и включать или
  выключать;
- **не усложнять.** До этой попытки другой агент развёл MCP и агента по
  отдельным приложениям, решение переусложнилось, и нормальную демонстрацию
  провести не удалось. Простота здесь — требование, а не пожелание.

**Развилки, которые выбрал пользователь** (спрашивали до начала работы):

1. *домен правой панели* — **клиенты и сделки**: карточка, статус (новый / в
   работе / оплачен / отказ), сумма;
2. *что включается и выключается* — **и сервер целиком, и каждый инструмент
   по отдельности**; при этом на экране должно быть ясно обозначено, где
   инструменты для агента, а где всё остальное;
3. *журнал обмена по MCP* — **нужен**, компактной лентой, строка раскрывается в
   сырой JSON;
4. *остатки прошлой попытки* (`data/spaceport.db`, пустые `agent/`, `server/`) —
   **удалить**, начать с чистого листа.

**Что сделано.**

- MCP-сервер «CRM» на официальном SDK: пять инструментов — `list_clients`,
  `get_client`, `create_client`, `set_status`, `stats`; данные в памяти
  процесса.
- Агент подключается к серверу **по сети** (streamable HTTP на `/mcp/`), хотя
  сервер живёт в том же процессе: так в журнале виден настоящий протокол, а не
  прямой вызов функций.
- Живая MCP-сессия: кнопка «Подключиться» / «Отключиться», состояние соединения
  с именем сервера, его версией и версией протокола, кнопка «Обновить список»
  (`tools/list` по требованию).
- Инструменты, полученные от сервера, уходят модели как function calling; вызовы
  идут обратно через MCP.
- Правая панель: выключатель сервера, галочки инструментов, таблица клиентов со
  сменой статуса, форма нового клиента, сброс данных.
- Журнал обмена: `initialize`, `tools/list`, `tools/call`, `shutdown`; клик по
  строке раскрывает подробности (схемы инструментов, аргументы, результат).
- Заход браузером на `/mcp/` больше не выглядит поломкой: вместо `400 Missing
  session ID` открывается страница-подсказка со ссылкой на интерфейс.

**Видео дня 16 пользователь снимает сам** — автоматический показ не готовился.

**Проверено живыми прогонами:**

- «Какие клиенты у нас в работе?» → один вызов `list_clients {"status": "в
  работе"}`, 2 033 токена, 9,8 с;
- «Заведи клиента ООО Заря на 90 000 и переведи Соколова в работу» → цепочка
  `create_client` → `list_clients` (модель сама нашла номер Соколова) →
  `set_status`, 4 143 токена, 14,4 с;
- выключение сервера закрывает соединение агента, попытка подключиться снова
  возвращает «MCP-сервер выключен в панели CRM»;
- снятая галочка инструмента убирает его из `tools/list` и из списка у агента.

## Архитектура

```
app/
  config.py      ключ, модель, порт, адрес MCP, обход прокси для localhost
  mcp_server.py  MCP-сервер CRM: данные, пять инструментов, выключатели
  agent.py       MCP-клиент (живая сессия), журнал обмена, вызов модели
  main.py        FastAPI: монтирует MCP на /mcp, отдаёт интерфейс и HTTP-API
static/
  index.html     весь интерфейс: две колонки, светлая тема, поллинг состояния
```

Пять файлов — сознательно. Пользователь следит за числом сущностей: появилось
ощущение «много файлов ради простой вещи» — это повод сокращать.

**Границы.** `mcp_server.py` ничего не знает про модель и про агента.
`agent.py` ничего не знает про FastAPI. `main.py` — только склейка и HTTP.
Интерфейс тонкий: он рисует состояние и дёргает четыре десятка строк API.

**Состояние и перерисовка.** И сервер, и агент держат счётчик `revision`;
`/api/state` отдаёт их сумму. Фронт опрашивает состояние раз в 1,2 с и
перерисовывает экран, только когда номер изменился. Поэтому правка справа сама
появляется слева и наоборот — без сокетов и подписок.

**Почему живая сессия, а не соединение на каждый запрос.** Задание дня — про
установку соединения, и на экране это должно быть видно: подключились,
получили список, отключились. Сессия держится в фоновой задаче (`McpLink._hold`):
войти в контекст клиента и выйти из него нужно **в одной и той же задаче**,
иначе anyio ругается на чужой cancel scope. Вызовы из других задач по уже
открытому клиенту — нормально.

## MCP SDK: важные детали (версия 2.2)

- **В SDK 2.x `FastMCP` переименован в `MCPServer`**: `from
  mcp.server.mcpserver import MCPServer`. Импорт `mcp.server.fastmcp` падает с
  подсказкой про миграцию. Код из статей и примеров под 1.x сюда не годится.
- Поля моделей стали **snake_case**: `tool.input_schema` (не `inputSchema`),
  `result.structured_content`, `result.is_error`.
- Высокоуровневый клиент — `mcp.Client`: принимает URL строкой,
  `StdioServerParameters`, транспорт или сам объект сервера (для тестов
  in-process). Используется как асинхронный контекст-менеджер; после входа
  доступны `client.server_info`, `client.protocol_version`, `client.instructions`.
- **Монтирование в FastAPI.** `mcp.streamable_http_app(streamable_http_path="/")`
  возвращает Starlette-приложение, его вешаем `app.mount("/mcp", mcp_app)`. У
  смонтированного приложения **свой lifespan не запускается**, поэтому менеджер
  сессий поднимается в lifespan основного приложения:
  `async with mcp.session_manager.run(): yield`. Без этого `/mcp` отвечает
  ошибкой. Свойство `session_manager` доступно только **после** вызова
  `streamable_http_app()`.
- **Адрес клиента — со слешем**: `http://127.0.0.1:8000/mcp/`. Без него уходит
  лишний 307-редирект на каждый запрос.
- **Ловушка с прокси.** Если в окружении задан `HTTP_PROXY` (VPN-клиенты ставят
  его глобально), запрос приложения к самому себе уходит на прокси и возвращает
  503 без единой строки в логах uvicorn — выглядит как поломка MCP. Лечится в
  `config.py`: `127.0.0.1` и `localhost` дописываются в `NO_PROXY`.
- **Отказ сервера отдавать телом JSON-RPC.** Клиент SDK разбирает тело
  non-2xx-ответа: если там JSON-RPC ошибка, наружу пойдёт её `message`, иначе
  человек увидит «Server returned an error response». Поэтому выключатель
  сервера возвращает `{"jsonrpc": "2.0", "id": 0, "error": {...}}` со статусом
  503, и в интерфейсе видно «MCP-сервер выключен в панели CRM».
- **`/mcp/`, открытый в браузере, отвечает `400 Bad Request: Missing session
  ID`** — это нормальная реакция транспорта на GET без сессии, а не поломка.
  Пользователь на это уже наступал, поэтому в middleware стоит проверка: GET с
  `Accept: text/html` получает страницу-подсказку со ссылкой на интерфейс, а
  настоящие клиенты (`Accept: application/json, text/event-stream`) проходят
  дальше как раньше.
- **Ошибки клиента прилетают группой.** Наружу вылетает `ExceptionGroup` — в
  интерфейсе от него толку нет, поэтому `agent._reason()` разворачивает группу
  и достаёт причину (у `MCPError` это поле `message`).
- `add_tool` / `remove_tool` меняют набор инструментов на живом сервере, но
  **уведомление `tools/list_changed` при этом не отправляется**. Поэтому после
  щелчка по галочке приложение само зовёт `tools/list` от имени подключённого
  агента — так список слева обновляется сразу.

## LLM API (важные детали)

- Base URL и ключ — из окружения (`DASHSCOPE_BASE_URL`, `DASHSCOPE_API_KEY`),
  режим OpenAI-совместимый, регион Singapore. Ключ в коде не хардкодить.
- **Рабочая модель — `qwen3.8-2.4t-a95b`** (переменная `MODEL`). У прошлых
  моделей курса свободная квота кончилась: `qwen3.8-max` — 16.09.2026,
  `qwen3.8-flash` — 17.09.2026, `qwen3.8-max-0902` — к концу третьей недели.
- **У этой модели thinking включён всегда.** Передавать
  `extra_body={"enable_thinking": False}` нельзя: API отвечает 400
  «The value of the enable_thinking parameter is restricted to True». Просто не
  передаём этот параметр; нестриминговый вызов при этом работает.
- Рассуждение оплачивается как выход: короткое «привет» стоит ~120 токенов,
  обращение с одним вызовом инструмента — ~2 000, с цепочкой из трёх — ~4 100.
- **Вызов инструментов работает** и проверен живыми прогонами: модель возвращает
  `tool_calls`, следом в диалог уходит по одному `{"role": "tool",
  "tool_call_id": …}` на каждый вызов.
- Ответ модели приходит с лёгкой Markdown-разметкой (`**жирный**`, списки).
  Интерфейс показывает жирное жирным (`markup()` в `index.html`), остальное — как
  есть; HTML экранируется.
- Ошибки API ловятся обобщённо в `/api/chat` и показываются в интерфейсе
  строкой, а не падением.

## Биллинг и защита от списаний

- Подсчёта бюджета в коде нет и не нужно: хватает бесплатных квот, а от
  реальных списаний защищает Stop-on-Exhaust (Free Quota Only) в консоли Model
  Studio. **Добавлять модель без включённого Stop-on-Exhaust нельзя.**
- Отдельного API «сколько квоты осталось» у Qwen нет — только веб-консоль.
- **Живой прогон — один раз и в конце работы.** Отладка идёт без обращений к
  модели: механика MCP, выключатели и данные проверяются HTTP-запросами к
  `/api/*`, это ничего не стоит.
- **Перед прогоном дороже ~20 000 токенов назвать цену и спросить.** Пользователь
  следит за квотой, письмо «Free Quota Used Up» для него — событие.

### Ключ API и секреты

`load_dotenv()` без `override`, поэтому настоящая переменная окружения побеждает
`.env`. Ключ тот же, что в прошлых неделях, файл уже перенесён. **Никогда** не
коммитить `.env`, не зашивать ключ в код, не логировать и не выводить в консоль.

## Проверка изменений

- Механику проверять запросами к HTTP-API при запущенном приложении: `/api/state`,
  `/api/mcp/connect`, `/api/tool`, `/api/server`, `/api/crm/*`. Модель при этом
  не вызывается — квота не тратится.
- Клиент `httpx` в проверочных скриптах создавать с `trust_env=False`, иначе
  системный прокси перехватит запрос к localhost.
- Временные скрипты держать **вне** каталога проекта (в каталоге сессии), чтобы
  случайный `git add .` их не захватил.
- Живой прогон связки «модель → MCP → CRM» — в конце, одним скриптом на два-три
  вопроса.

## Правила работы над проектом

### Язык
Общение с пользователем — по-русски. Комментарии и тексты интерфейса — тоже.

### Порядок работы над заданием

1. пользователь показывает задание скриншотом — ассистент его выполняет, держа в
   уме будущую демонстрацию: по ходу помечает, что будет видно на экране, какие
   кнопки участвуют и какие вопросы агенту дают наглядный результат;
2. по итогам — сначала короткое человеческое объяснение: что сделали, зачем это
   нужно и что даёт (тон менеджера, представляющего доработку акционерам), затем
   план демонстрации пронумерованными шагами «что делаем → что должно быть
   видно», затем короткий проход по удобству: какие сценарии прошли по экрану и
   где пришлось думать;
3. по команде **«демонстрация»** ассистент проводит показ и записывает видео.

### Перед крупным решением — спросить
Домен, набор сущностей, что именно включается и выключается, как выглядит экран —
это развилки пользователя. Предлагать 2–3 варианта с рекомендацией и коротким
описанием последствий, а не решать молча.

### Git — читать можно, менять нельзя
- **Разрешено:** `status`, `log`, `diff`, `show`, `blame`, `branch`, `ls-files`.
- **Запрещено:** `add`, `commit`, `push`, `pull`, `fetch`, `merge`, `rebase`,
  `reset`, `checkout`/`switch` со сменой состояния, `stash`, `restore`, `clean`,
  правка git-конфигов. Версиями, ветками и коммитами занимается **только
  пользователь**. Нужен коммит или пуш — написать пользователю готовую команду и
  зачем она.

### Никаких следов AI-агента в коде
Код уходит в репозиторий, который видят другие:
- никаких упоминаний ассистентов и AI в коде, комментариях, именах файлов,
  сообщениях коммитов;
- не добавлять трейлер `Co-Authored-By: …` и ссылки на сессию ассистента — даже
  в готовой команде коммита, которую отдаёшь пользователю. Это правило проекта,
  оно важнее общих настроек по умолчанию.

### Этот файл — вне git
`CLAUDE.md` и папку `.claude` исключать через `.git/info/exclude` (а **не**
`.gitignore`: он сам попадает в репозиторий и выдал бы их имена). Строки в
`.git/info/exclude` добавляет пользователь. Следствие: `git restore` этот файл
не откатит, правь аккуратно.

### Никаких ссылок на этот файл из кода
Файла нет в репозитории — ссылки на него вели бы в никуда.

### Когда обновлять этот файл
Только после того, как пользователь подтвердил, что файл нужно обновить. При
обновлении — дописывать новый день и правки в архитектуру, а не переписывать
целиком.

## Предпочтения пользователя по интерфейсу

- **Тема — дневная, но приглушённая.** Прямая просьба дня 16: «сделай светлую
  для разнообразия, зелёную или жёлтую, но чтобы не убивало глаза». Первый
  вариант вышел почти белым («не такое светлое, что ты из крайности в крайность
  прыгаешь»), после чего пользователь попросил ещё на 30 % темнее. Рабочая
  палитра — шалфейно-оливковая со светлотой основных площадей 56–65 %: левая
  половина `#9ca888`, правая `#94a07f`, карточки `#a8b28d`, поля `#aeb891`,
  акцент `#17351c`. Белый фон и возврат к тёмной теме — только по просьбе. При
  затемнении гасить и насыщенность (в HSL: `L×0.7`, `S×0.7`), иначе зелёный
  уходит в кислотный.
- **Затемнили фон — затемняй текст и увеличивай кегль.** Следующая же претензия
  после затемнения: «тёмный текст на тёмном фоне, ничего не видно». Текст
  `#101508`, второстепенный `#1b2413`; контрасты 6,7–8,9:1 и 5,8–7,7:1. **Любую
  правку палитры проверять расчётом контраста, а не на глаз** — за день 16 тема
  переделывалась трижды, и каждый раз спасал бы расчёт, а не «кажется, видно».
- **Шрифт крупный.** После двух просьб подряд («шрифт побольше», «ещё на 20 %»)
  база 20,5 px, заголовки половин 27,5 px, заголовки карточек 23 px, имена
  инструментов 20 px, их описания 18 px, строки клиентов 20,5 px, журнал 18 px,
  мелкие метки 15,5 px. Меньше делать не нужно: это размер, при котором
  пользователь согласился, и он же хорошо читается на видео. Увеличивая кегль,
  сразу подгонять раскладку (высота поля ввода и кнопки, ширина колонки метода
  в журнале, ширина тумблера и поля суммы) — иначе элементы жмутся.
- **Половины экрана должны читаться как две разные области.** Тонкой линии
  оказалось мало (пользователь отметил это стрелкой на скриншоте): теперь у
  половин разный фон, между ними разделитель 3 px `#6b8159` и внутренняя тень
  на правой панели. Контрасты проверяются расчётом WCAG, а не на глаз: текст
  8,8–10,7:1, второстепенный — не ниже 4,5:1.
- **Экран делится на понятные зоны с подписями.** Отдельная просьба дня 16: на
  правой панели должно быть ясно, **где инструменты для агента, а где всё
  остальное**. Поэтому три карточки с заголовками: «MCP-сервер», «Инструменты
  для агента», «Данные CRM».
- Минимализм: новая функциональность встраивается в основной экран, а не
  выносится в отдельный раздел.
- Лишние сущности пользователю не нравятся: он следит за числом файлов и за тем,
  чтобы каждый был нужен.
- Кнопка не должна дублировать то, что делает другая.
- Созданное должно правиться и удаляться, а не копиться и пересоздаваться.
- Техническая изнанка — в раскрывающийся блок, а не в каждый ответ. В обычном
  режиме под ответом остаётся одна человеческая строка (здесь: какие инструменты
  вызваны, сколько токенов и секунд).
- Терминология — из ИИ-инженерии: «инструменты», «сессия», «протокол»,
  «транспорт». Новые понятия называть принятым термином, а не бытовым словом.
- **Отвечать коротко.** «У тебя был слишком раздутый текст в прошлый раз, его
  трудно воспринимать» — сказано дважды за прошлые недели. Просят список шагов —
  давать список шагов, без вступлений и таблиц-простыней. Развёрнутое
  объяснение — когда спрашивают «что думаешь» или «почему».
- Пользователь запускает приложение сам и проверяет руками — после правок давать
  команду запуска и короткий список того, что стоит нажать.
- Демо-сценарий нельзя предлагать непрогнанным: перед тем как отдавать список
  вопросов агенту, прогнать его целиком.

## Демонстрация результата на видео

Формат сдачи — видео + код. Запись экрана: Bandicam Portable
(`C:\Program Files (x86)\Bandicam Portable\Bandicam_Portable.exe`), включение и
остановка — F12, второй монитор уже выбран пользователем.

В третьей неделе показ вёл скрипт-оператор (`demo_operator.py`) на PySide6:
он двигал мышь, печатал по буквам и жал F12. **Сюда этот скрипт не переносился** —
интерфейс теперь веб, и механика управления окном другая. Если пользователь
попросит автоматический показ, сначала обсудить способ (браузер под управлением
скрипта — отдельная задача), а не переносить старый оператор.

Что стоит помнить из прошлого опыта записи:

- сначала поднять Bandicam и убедиться, что процесс `bdcam.exe` жив, и только
  потом начинать показ: на дне 15 первый дубль ушёл без записи;
- перед записью привести состояние к исходному: сбросить данные CRM, очистить
  чат, отключить MCP — тогда показ начинается с нуля и видно, как соединение
  устанавливается;
- показывать только то, что гарантированно работает: сценарий прогнать заранее.
